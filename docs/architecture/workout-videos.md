# Видео выполнения упражнения

Видео прикрепляются к **сохранённому результату завершённой тренировки**:
`workout_sessions.id` + UUID конкретного `exercises[].id`. Имя упражнения,
позиция в массиве и ID упражнения в каталоге не являются ключом ролика.
Можно хранить до восьми роликов на одно выполнение упражнения.

Миграция `0011_workout_videos` добавляет приватные метаданные и однократно
заполняет UUID существующих упражнений выполненных тренировок, сохраняя
массивы, подходы, заметки и snapshots. Новые упражнения получают UUID;
редактирование и перестановка сохраняют его. Копирование плана и создание
результата из плана создают новые UUID. Исправление результата без UUID
отклоняется с 409: безопасного сопоставления по имени/индексу нет.

## Устройство и формат

Выбор через системный picker `video/*,.mov,.mp4`, затем лениво загружается
Mediabunny 1.61.4. Input читает Blob по запросу; исходный файл не отправляется
на сервер и не сохраняется приложением на устройстве. Ограничения:
исходный файл до 1 ГиБ, длительность до 5 минут, результат до 256 МиБ.

Проверяются декодер исходного видео и AVC-encoder браузера. Конвертация
всегда принудительно перекодирует видео в H.264, 30 кадров/с; картинка
вписывается в 1280×720 либо 720×1280 без увеличения исходного разрешения.
Rotation/flip и pixel aspect ratio учитывает Mediabunny; ориентация
запекается в пиксели (`allowTransformationMetadata: false`). Контейнер —
fragmented MP4; выход накапливается ограниченными Blob-частями. Metadata tags
исходника не переносятся. AAC копируется без перекодирования; другой звук
требует AAC-encoder. Это необходимо в Chromium Linux, где декодирование AAC
доступно, а кодирование отсутствует. Неподдерживаемые дорожки не удаляются
молча: вместо частичного результата показывается ошибка.

HEVC/MOV зависит от доступного браузеру декодера, версии ОС и аппаратуры.
Наличие расширения `.mov` не подтверждает поддержку кодека. При ошибке
**оригинал не загружается**, кнопки отправки нет; предлагается выбрать другой
файл/использовать поддерживаемый Safari/H.264 запись. Успешный результат
показывается существующим Video.js. Отправка требует отдельного нажатия.

## Приватная загрузка и возобновление

- `GET /api/workouts/videos?ownerId=…&sessionId=…`: metadata/status/подтверждённые части.
- `POST /api/workouts/videos?ownerId=…`: создаёт запись для UUID упражнения.
- `PUT /api/workouts/videos/{id}/parts/{part}?ownerId=…`: часть по 4 МиБ,
  последняя — остаток. Повтор той же части идемпотентен по SHA-256,
  другие байты для подтверждённой части дают 409.
- `POST /api/workouts/videos/{id}/finalize?ownerId=…`: проверяет наличие частей,
  инспектирует MP4/AVC, звук, размер картинки, duration и FPS без декодирования
  на сервере. Затем проверяет хеши и потоково собирает приватный объект.
  Повтор finalize готового ролика идемпотентен. Части удаляются после успеха.
- `GET/HEAD /api/workouts/videos/{id}/playback?ownerId=…`: авторизованное
  воспроизведение, single byte Range (206), suffix/open-ended, 416 для
  неподдерживаемого/multipart/неразрешимого Range. `private, no-store`.
- `DELETE /api/workouts/videos/{id}?ownerId=…`: удаляет ролик или незавершённую
  загрузку и её части.

XHR показывает прогресс отправки; request timeout 90 секунд. После ошибки
пользователь продолжает с подтверждённых частей — без повторной отправки
успешных. После остановки/перезагрузки сохраняется только сжатый черновик
в IndexedDB, scoped по owner/session/exercise; TTL 24 часа, удаление при
выходе из аккаунта и успешной отправке. Просроченные локальные записи
физически очищаются при следующем обращении. Если IndexedDB недоступна или
квота заполнена, UI предупреждает, что вкладку закрывать нельзя.

При `document.hidden` сжатие/активная отправка отменяются; возвращение
перепроверяет доступ. Обработка не возобновляется молча: сжатие начинается
заново, загрузка — кнопкой «Продолжить». **Фоновая работа на iOS не обещается**;
ОС может выгрузить страницу или вытеснить её storage. Незавершённые серверные
попытки старше 24 часов удаляются при следующем создании загрузки владельцем;
не больше десяти активных попыток на owner.

## Storage и доступ

Используется `getObjectStorage()` и существующие S3/SeaweedFS переменные,
бакет и ключи. Новых сервисов, секретов, presigned/public URL и permissions
нет. Ключи `workout-videos/{randomUUID}/part-N` и `…/video.mp4`. `put/get`
старых потребителей и cap buffered get 100 МиБ сохранены. Добавлены
`putStream` и `readStream` с Range: fs использует atomic rename/Node streams,
S3 — тот же SDK/client/config и потоковые PutObject/GetObject. Опциональный
checksum отключён (`WHEN_REQUIRED`) для совместимости streaming с S3 APIs.
Сервер держит в памяти по одной части, не весь ролик.

Каждый list/upload-part/finalize/delete/playback/HEAD/Range авторизует ownerId.
Запись только OWNER (`workouts:log`), чтение OWNER либо TRAINER с текущим
`trainer_access` (`workouts:read`). Grant также перепроверяется между частями
finalize и при каждом pull playback-потока. После отзыва новые Range запрещены,
активный поток прерывается при следующем pull. Уже полученные браузером
байты отозвать невозможно. Удаление упражнения/результата сразу прекращает
его доступность и очищает связанные объекты. Один Node process — существующий
контракт приложения; локальные locks сериализуют операции одного upload.

## Проверки

Только synthetic FFmpeg testsrc/sine clips и synthetic accounts; реальные
материалы/production storage не используются. Vitest проверяет UUID,
миграции с сохранением истории, несколько частей/retry/conflict/finalize,
доступ/отзыв во время потока, malformed media, Range, fs поток выше cap
100 МиБ и настоящий SDK stream/Range на loopback S3 fixture. Playwright
запускается на production build в облаке: desktop и mobile viewport,
MOV orientation, preview, interruption/reload/resume, Video.js playback,
trainer grant/revoke, HEVC capabilities, отказ unsupported input и suspend.
Mobile Chromium emulation не является проверкой физического iPhone/Safari.
Live SeaweedFS deployment не выполняется этой feature-веткой.
