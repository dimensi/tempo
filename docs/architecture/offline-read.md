# Owner offline read API

The automatic OWNER browser cache consumes version-1 `src/contracts/offline.ts`. This server layer only reads existing local SQLite records, private photo files and a purpose-limited local TransformMate connection binding. It makes no SDK, provider, refresh-token, media URL, or upstream request. No app data writes, schema, grants, dependencies, keys or credentials are added. Better Auth retains its existing session validation/renewal behavior.

## Routes and authorization

- `GET /api/offline/identity` accepts no query and returns an opaque owner partition, opaque connection generation, OWNER role, server time, session expiry and server expiry observation, plus the current weight policy version.
- `GET /api/offline/snapshot?from=YYYY-MM-DD&to=YYYY-MM-DD` accepts precisely one of each parameter, inclusive at most 30 calendar dates. No owner selector or duplicate/unknown parameter is accepted.
- `GET /api/offline/photos/<opaque>?date=YYYY-MM-DD` accepts precisely one date. The opaque photo key is resolved only in that session owner's photos for that date. It never exposes native YAZIO photo IDs, which embed the owner ID.

All routes derive the owner from the current real session. Anonymous/expired sessions receive 401; TRAINER receives 403 even with a grant. Before local reads and after awaited binding/file work, all three existing `nutrition:read`, `measurements:read`, `workouts:read` permissions are checked with explicit owner scope. Session ID, owner ID, role and expiry must remain valid. Snapshot/photo release rechecks connection generation; photo release also checks that its current local storage key still matches. Responses are `private, no-store`, vary on Cookie and use `nosniff`. Error DTOs contain a fixed code only.

HMAC-SHA256 uses the existing `BETTER_AUTH_SECRET` with distinct purpose strings. Partition binds owner identity; connection generation binds owner, current session ID, YAZIO schedule epoch and local TransformMate configured/stable connection ID. No hash is an authentication credential. Refreshing a TransformMate token retains its stable connection ID and does not invalidate the partition; disconnect/reconnect changes the generation. The tiny `readTransformMateOfflineBinding` helper returns only configured Boolean, connection ID and a noncredential revision after the existing store validates/decrypts local ciphertext, never its credential or profile payload. Missing storage is disconnected; invalid storage fails closed.

The local binding helper also captures a noncredential revision inside the existing token-store serialization. Stable binding mutations advance that revision synchronously before their file write; ordinary refresh with the same connection ID does not. Each final release synchronously fences both this revision and the YAZIO epoch after its last async authorization check. A disconnect/reconnect during that check therefore cannot release an older binding.

The genuine server `expiresAt` observation remains `min(serverNow + 24 hours, minimum session expiry observed across every authorization check)`. It does not determine downloaded local-copy retention. The guard returns the latest validated session while retaining the earlier expiry cap even if a later check renews it. A server response does not prove continued authorization while offline; the browser owns authenticated OWNER device eligibility, calendar retention, clock rollback checks, generation fencing and purging on identity/logout/connection changes. Live requests retain the existing server authorization checks.

## Data projection and limits

Snapshots contain safe diary entries/totals; photo metadata; all manual measurement values and notes; in-range raw YAZIO weights with account-specific `unit:kg` / `unitStatus:OWNER_CONFIRMED`; in-range nullable daily step observations; in-range planned workouts and local sessions; available cached TransformMate actual facts/metrics; and already-persisted native TransformMate training snapshots for the current confirmed account binding. Owner IDs, profile/account data, source locators, signed URLs, remote exercise/occurrence/protocol IDs and token payloads are omitted. Canonical browser-visible readonly workout hrefs are strict route locators; native hrefs contain the training ID already visible in the ordinary URL. Record keys are purpose-separated opaque HMACs. This application’s OWNER explicitly confirmed that they enter YAZIO weights in kg. Projection applies that account assumption without conversion; raw persisted values, NULL SDK units and upstream UUIDs remain unchanged. A preference such as `unitContext:lb` is not treated as evidence or converted. Zero, null and missing dates are preserved. Ambiguous provider weight dates cannot establish range membership, so they are excluded from a dated snapshot.

Photo `availability:'metadata-only'` explicitly means bytes were not checked/downloaded by the snapshot. The browser must track each authenticated photo download separately and must not claim all photos are saved from metadata alone. Server photo responses are at most 10 MiB; the frontend owns its aggregate image quota.

SQL predicates constrain owner and requested dates. Plan rows are restricted to overlapping plan intervals, then only their in-range workouts are projected. Queries fetch at most N+1 rows and throw 413 on overflow: 30 diary/step days, 300 photos/weights/sessions/cached facts, 1000 measurements, 200 overlapping plans. No truncation result is returned. JSON fields are capped at 2 MiB inside SQL; iteration applies a shared 4 MiB raw-payload budget before accumulation/projection; the final safe JSON must also fit 4 MiB. Oversized projections fail explicitly. Native training SQL additionally requires the current confirmed account scope and probes 301 rows against a 300-row cap; absent binding yields no native rows. Disconnected binding may retain that confirmed account’s history. Other owners/accounts and out-of-window dates are excluded. Native rows share the 2 MiB row and 4 MiB total budgets, with explicit overflow errors. No external reads are used to fill gaps or missing cached facts.

Errors: `OFFLINE_ACCESS_DENIED` (401/403), `OFFLINE_INVALID_REQUEST` (400), `OFFLINE_LIMIT_EXCEEDED` (413), `OFFLINE_CONNECTION_CHANGED` (409), `OFFLINE_UNAVAILABLE` (503; absent photo 404). No raw exceptions or record contents are logged or returned.

## Verification

Focused synthetic tests use genuine seven migrations and real Better Auth owner/trainer sessions. They cover strict date/query bounds, trainer denial despite grants, no provider fetch, safe ID/URL stripping, zero/null facts, notes/workouts, post-read session revocation, expired sessions, schedule-epoch changes, SQL row overflow, oversized per-row/cumulative payload, and stable-refresh/disconnect/reconnect/corrupt local binding. No production credentials, private records or provider probes are used.

## Transparent application and device retention

The browser now automatically populates an OWNER device copy after fresh authenticated identity verification. The opt-in switch and standalone reader UI are removed. The static bundle presents ordinary URLs using the shared application frame, diary/date navigation and workout read components; the connected Next adapters and server permissions remain authoritative online. Static document navigation fallback covers nested workout routes, while API and RSC requests remain network-only. Network-required sections explicitly explain their limitation. Unknown diary dates/details show the inline Russian unavailable-data message, and mutation controls are disabled without a queue.

The strict snapshot adds bounded canonical browser-visible readonly workout hrefs, known loaded dates, parent/session links and safe plan snapshots. Native hrefs contain the numeric training ID already visible in the ordinary URL; no separate remote IDs, exercise/protocol identifiers, owner IDs, account scopes, credentials or signed URLs enter the DTO. This explicitly replaces the earlier blanket URL-ID stripping rule. Required fields invalidate and physically erase old snapshots/photos before authenticated refill.

Diary/photos and related dated observations keep the rolling 15 local calendar dates. Workout collections retain already-captured older dates independently, within existing row limits and the 4 MiB device JSON quota; 300 known dates bound coverage. Visiting older ordinary workout routes or completing their normal reads triggers a local-only authenticated snapshot capture for that date. Refresh replaces the captured date range and preserves older bounded workout copies. Nothing fetches missing provider facts or videos. Current UI does not provide offline comments, catalog/exercise descriptions, analytics, measurements, settings or PDF.

Automatic cache activation is blocked by a same-origin Web Lock while an auth/provider mutation holds purge-before/request/final-purge. Existing identity/role/account/provider epochs, durable blocker, CAS generation, online denial/timeout concealment, cross-tab notifications, BFCache concealment, independent expiry observations and clock rollback controls remain. There is no browser 24-hour TTL or offline authorization extension.

Production browser cases now run once after the existing CI build using tests/offline/production.config.ts; the generic development suite excludes those cases. No dependencies, DB schema, auth configuration, SDK behavior or deployment changed.
