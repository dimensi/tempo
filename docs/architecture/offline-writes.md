# Offline writes (v1)

The durable queue remains supported under [ADR 002](../decisions/002-resilient-client-reads.md). Its persistence/server guarantees below remain valid. The queue uses the current account, Web Locks and common API transport independently of snapshots or a Service Worker. Cold offline boot, a full read snapshot and synchronous BFCache conceal are not queue requirements.

Scope: local workout sessions (sets, weights, repetitions, date, title, notes) and manual measurements only. OWNER and granted TRAINER workout forms use the same durable queue, including exercise additions, sets, results and lifecycle transitions during an active workout. Manual measurement writes remain owner-only. Ordinary forms commit to the same queue as the disconnected capture forms on `/workouts` and `/measurements`. Online forms then attempt foreground synchronization and retain the existing detail navigation after acknowledgement; a pending result remains available in the device queue. Native TransformMate workouts, settings, documents, uploads, deletes and other people's data are outside this queue. Workout permissions are identical for owners and granted trainers; external-service connection management remains owner-only.

## Persistence and synchronization

`src/contracts/offline-write.ts` defines an account-partitioned, UUID operation and record ID, original version, YAZIO connection epoch and validated discriminated payload. `src/lib/offline-write-queue.ts` stores the edited record and immutable operation in **one strict IndexedDB read/write transaction**, resolving only on completion. An aborted/quota transaction publishes neither result nor success. The form remains populated on failure. Normal reload/tab closure retains committed data; this guarantees persistence, not that Next.js can boot without a network. Browser/user eviction is not preventable. Storage/Web Locks must be available, otherwise saving fails explicitly.

The write database (`yazio-offline-writes-v1`) is separate from the read database. Read-cache purge cannot delete writes. Calendar retention removes only old acknowledged manual measurements; pending/review variants are never removed by age. Workouts follow the existing independent workout retention. Pending operations are capped at 1000 and the whole state at 4 MiB; old acknowledged operation history may be compacted to 100 entries, while server receipts remain durable. The authenticated catalog is bounded to 500 manual measurements and 500 local sessions, with explicit failure rather than truncation.

The current implementation uses a shared auth/device lock. Preserve the locks needed for atomic saves, account changes and queue integrity while removing read-shell/device requirements under ADR 002. An exclusive same-origin Web Lock serializes sending across tabs. Local saves do not wait for network requests. IndexedDB serializes concurrent edits. Operations for the same record wait for their predecessor, which supplies the acknowledged base version before the next operation's first send. Other records can continue when one record needs review. Transport/5xx/429 failures use bounded exponential delays (2-second basis, 5 attempts, 5-minute ceiling); validation/access/conflict errors require review. A persisted `sending` state is recovered using the same UUID and body. Manual rechecking of uncertain outcomes also replays that UUID; it cannot create a duplicate alternative blindly.

Opening, returning to a visible application, focus, online events and a 15-second foreground timer attempt synchronization. Background Sync is not used. At most 10 operations are sent per pass. Confirm the authenticated account before draining; each server request independently derives the owner from the current session or trainer grant and checks the operation permission. Trainer partitions bind the reader, role and granted owner and match the shared read context; owner partitions retain their existing identity. Client owner selection is never accepted. Under the accepted target, displaying already loaded records/drafts does not wait for an online identity check, and BFCache restore does not conceal fields. Reconnect/focus/pageshow checks run in the background. The common auth-error handler resets client state after a confirmed session-wide denial; ordinary transport failure leaves records and input available. Queue initialization/sending must not depend on a shell, snapshot or worker readiness.

## Server atomicity and conflicts

`GET /api/offline/writes` returns a private/no-store catalog without owner IDs or credentials: owners receive workouts and measurements, while granted trainers receive workouts only. `POST` requires the configured trusted Origin, a genuine session, the current owner grant for trainers, the operation permission (`workouts:plan` for workout edits, `workouts:log` for transitions/feedback, or owner-only `measurements:write`), a matching HMAC account partition and valid v1 input. The server applies a result and its owner+operation receipt in one synchronous SQLite transaction. Replaying an accepted operation returns its original receipt even after later changes; reusing the UUID with another body fails. Migration `0015_offline_write_receipts.sql` adds only the receipt table, foreign key and composite primary key.

Workouts use their existing monotonically increasing revisions. Manual measurement versions are SHA-256 of their canonical validated editable contents, so writes from the ordinary API are also detected. The form retains the version from when editing started, even if a background refresh arrives. Creation against an occupied ID or update against a changed/missing record conflicts. A linked workout creation also checks its original plan revision and snapshots the plan through the existing repository. Offline edits cannot remove exercise occurrences that could own private videos. Adding occurrences uses the same queue for both roles; removing saved occurrences uses the online save path and video cleanup.

A conflict preserves the local variant and offers either the current server variant or an **explicit separate local record**; it never silently overwrites. Unknown/validation/access outcomes offer rechecking with the same operation ID, not a potentially duplicate create. Offline newly entered workouts are independent local sessions; native TransformMate writes remain online-only.

Manual measurements atomically enqueue through the existing YAZIO outbox. That worker reads the remote date summary before writing and reconciles uncertain outcomes; the browser does not assume provider idempotency or retry the provider API. A changed YAZIO schedule epoch rejects a not-yet-applied measurement for review, while an existing receipt can still be acknowledged. Local workout writes attempt best-effort TransformMate synchronization after the durable local commit; provider failures do not roll back that commit. “Синхронизировано” acknowledges the application's durable local server record; YAZIO delivery has its existing separate measurement status.

## Logout

An explicit logout checks pending/review/sending operations and offers staying to synchronize or explicitly deleting device records and logging out. Storage failure does not prevent server sign-out, and cleanup failure must not be reported as successful physical deletion. Offline logout records durable sign-out intent until server confirmation; ordinary read-cache eviction is not a logout and never deletes pending writes.

Expired-session records stay associated with the original account and owner and cannot be displayed/sent by another account or adopted into its queue. No pending record is silently aged out. The accepted target uses common client logout/reset handling and ordinary account/request-generation checks, without per-frame DOM concealment or a BFCache protocol. A provider-account epoch used to prevent incorrect upstream writes remains a write-correctness check, not a reason to close cached read screens.

## Targeted verification and manual scenario

Choose checks using the tiers in [AGENTS.md](../../AGENTS.md). Runtime queue/lifecycle changes require Full verification plus the affected production browser scenarios. Historical release permissions, old suite counts and cold-shell tests do not define new acceptance. Record only commands actually executed for the current revision; browser emulation is not physical-device proof.

Preserve tests for commit/abort boundaries, reopening the IndexedDB store, read-cache/queue separation, quota failures, bounded retries, lost responses, sending recovery, dependent ordering, stale versions, account separation, SQLite receipt atomicity and real-session API authorization. Remove shell/cold-boot assumptions when updating the client lifecycle, without weakening server or write-integrity assertions.

Manual acceptance scenario (not executed by this documentation change):

1. Sign in as OWNER online, open workouts and measurements and load the normal forms/catalog.
2. Disable the network in the already open application. Save a local workout and a manual measurement; both report device persistence only after transaction completion.
3. Reload/reopen the application after restoring network access and verify both committed records survived. Test storage reopening separately from application boot; launching the ordinary URL while offline is not required.
4. Reconnect two existing tabs and synchronize. Confirm one server session and one manual measurement, including after another reopen/reconnect.
5. Lose a POST response after server acceptance, edit a record elsewhere, attempt logout with pending records, and simulate quota failure. Verify deduplication, preserved conflicts, explicit logout choice and retained input.

The receipt schema and server migrations do not change as part of the client simplification. No production data is used for fixtures. Merge/deploy requires authorization for the current task; this document grants none.
