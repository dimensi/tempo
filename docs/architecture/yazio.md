# YAZIO integration

The app consumes committed `vendor/yazio` via `file:vendor/yazio`: source revision `89386f0db1ef15bc2bb21b359805d83c9fc7bbf7`, package `1.1.3-vendor.89386f0`, with its own Zod 3 dependency. The adapter follows installed declarations for daily summary, consumed items, product/recipe references and meal images. It verifies meal-image capability before sync so an incompatible SDK cannot silently clear photo slots. The image includes the same SDK and an offline capability smoke check.

`src/server/yazio/client.ts` constructs the library through an injected token store and maps failures to generic errors without exposing tokens or personal payloads. `fileTokenStore()` validates metadata and atomically persists refreshes with mode 0600. The operator configures persistent `YAZIO_TOKEN_FILE` outside Git, public files and uploads. The owner can save existing Token JSON through `/settings/yazio`; email/password connection UI is pending even though the SDK supports login and refresh. Persistent token-store setup requires separate operator approval. SDK metadata includes `token_type`, `access_token`, `refresh_token`, `expires_in`, `expires_at`; never guess expiry. An MCP API key is not a YAZIO token. The older private yazio-sse Worker uses its MCP API key separately from `YAZIO_USERNAME`/`YAZIO_PASSWORD`; do not copy any values into docs or treat these credentials as interchangeable.

Owner-only `/api/yazio/status` reports whether a token-file path is configured, whether a validated stored token exists, and persisted sync status. It does not prove upstream connectivity. Browser responses expose no token values or file paths. The current preview has no real token, so live account sync remains unverified.

The owner requests `/api/yazio/sync` for an inclusive period up to 366 days or a recent range of 1–31 days ending at an explicit date. Days run serially; reference lookups are deduplicated, bounded and cached per owner for 24 hours. Photo work has its own bound. There is no scheduler or automatic retry. Overlapping owner sync is rejected within the supported single process; a new run replaces stale running status after interruption.

Validated payloads are normalized to exact decimal contracts before persistence. Unknown/ambiguous values retain issues; calculated, known, official and delta totals remain distinct. A successful day and current YAZIO photo metadata replace atomically. Fetch/reference/photo/normalization failures preserve the old day. Successful empty responses remove prior upstream entries/photos; manual photos survive sync.

Image fetches require checked HTTPS `images.yazio-cdn.com` URLs, pin a validated public DNS address, reject redirects and never forward bearer tokens to the CDN. JPEG/PNG/WebP must match signatures and byte limits. Content-addressed files use mode 0600 under a private 0700 directory. Read handlers authorize owner scope and recheck grants after file I/O. Browser metadata omits source URLs/storage keys. Unreferenced files remain; physical garbage collection is an operator concern.

Public readers in `@/server/nutrition` require headers and owner ID, including `nutritionDayExists()` for comments. Trainers may read with current grants but cannot sync, manage tokens or mutate manual photos. Mutations enforce same origin. Versioned migrations create snapshots/cache/status/photo metadata; tests use genuine migrations. Root Vitest includes the nutrition-sync suite.

Tests use synthetic upstream data and real login/grant/revocation scenarios, not the owner's upstream records or credentials. After the user configures an existing token, verify status, bounded sync, diary totals/issues and private photos through real HTTPS. API details are in [nutrition sync](../nutrition-sync.md); current SDK, migration and test-discovery status is recorded here.
