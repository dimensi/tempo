# YAZIO integration

The app consumes committed `vendor/yazio` via `file:vendor/yazio`: source revision `89386f0db1ef15bc2bb21b359805d83c9fc7bbf7`, package `1.1.3-vendor.89386f0`, with its own Zod 3 dependency. The adapter follows installed declarations for daily summary, consumed items, product/recipe references and meal images. It verifies meal-image capability before sync so an incompatible SDK cannot silently clear photo slots. The image includes the same SDK and an offline capability smoke check.

The OWNER connects in `/settings/yazio` by submitting their own email/password over HTTPS and explicitly consenting to persistent connection storage. `POST /api/yazio/connect` authorizes owner scope before and after the SDK's `getTokenFromCredentials({username,password})` exchange, awaits encrypted token persistence, and returns only `{configured:true}`. An unconfigured store is rejected before exchange. Password/email exist only in request memory; no browser storage, DB/file, log, error or response persists them. The UI clears the password at submission and on completion. JSON import remains an advanced optional fallback. SDK metadata includes `token_type`, `access_token`, `refresh_token`, `expires_in`, `expires_at`; never guess expiry. An MCP API key is not a YAZIO token.

`fileTokenStore(path, ownerId, secret)` stores strict version-1 AES-256-GCM envelopes with random 12-byte nonce, 16-byte tag and authenticated owner/context/version/generation. HKDF-SHA256 derives the key from the existing `BETTER_AUTH_SECRET`; no new persistent key is generated. Writes are atomic with mode 0600 (new directory 0700), serialized per path in the supported single process. The operator configures `YAZIO_TOKEN_FILE` outside Git/public/uploads only after separate approval; no production path is activated by this implementation. There is no plaintext fallback. Legacy JSON requires an explicit operator migration or user reconnection.

`src/server/yazio/client.ts` shares one in-flight authentication/refresh per client and awaits persistence even though the SDK does not await its `onRefresh` callback. Callback rejections are handled and upstream errors are generic. Loaded connection generations are checked before/after authentication and on saves. Confirmed `POST /api/yazio/disconnect` writes an authenticated encrypted null tombstone and rotates generation; stale refresh/delayed connect cannot resurrect tokens. Disconnect preserves nutrition snapshots/photos. Backup/restart must retain the encrypted file, the same auth secret and owner identity; secret rotation requires explicit migration or reconnect, never silent fallback.

Owner-only `/api/yazio/status` reports whether a token-file path is configured, whether a validated stored token exists, and persisted sync status. It does not prove upstream connectivity. Browser responses expose no token values or file paths. The current preview has no real token, so live account sync remains unverified.

The owner requests `/api/yazio/sync` for an inclusive period up to 366 days or a recent range of 1–31 days ending at an explicit date. Days run serially; reference lookups are deduplicated, bounded and cached per owner for 24 hours. Photo work has its own bound. There is no scheduler or automatic retry. Overlapping owner sync is rejected within the supported single process; a new run replaces stale running status after interruption.

Validated payloads are normalized to exact decimal contracts before persistence. Unknown/ambiguous values retain issues; calculated, known, official and delta totals remain distinct. A successful day and current YAZIO photo metadata replace atomically. Fetch/reference/photo/normalization failures preserve the old day. Successful empty responses remove prior upstream entries/photos; manual photos survive sync.

Image fetches require checked HTTPS `images.yazio-cdn.com` URLs, pin a validated public DNS address, reject redirects and never forward bearer tokens to the CDN. JPEG/PNG/WebP must match signatures and byte limits. Content-addressed files use mode 0600 under a private 0700 directory. Read handlers authorize owner scope and recheck grants after file I/O. Browser metadata omits source URLs/storage keys. Unreferenced files remain; physical garbage collection is an operator concern.

Public readers in `@/server/nutrition` require headers and owner ID, including `nutritionDayExists()` for comments. Trainers may read with current grants but cannot sync, manage tokens or mutate manual photos. Mutations enforce same origin. Versioned migrations create snapshots/cache/status/photo metadata; tests use genuine migrations. Root Vitest includes the nutrition-sync suite.

Tests use synthetic OAuth/upstream and real login/grant/revocation scenarios, not the owner's upstream records or credentials. The connection browser regression is included in root Vitest/CI and exercises SDK exchange, encrypted save, failure/busy reset, unconfigured explanation and confirmed disconnect. After separately approved store setup and deployment, the user supplies their own account credentials and verifies status, bounded sync, diary totals/issues and private photos through real HTTPS. API details are in [nutrition sync](../nutrition-sync.md).
