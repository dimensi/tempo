# YAZIO integration

The app consumes committed `vendor/yazio` via `file:vendor/yazio`: source revision `89386f0db1ef15bc2bb21b359805d83c9fc7bbf7`, package `1.1.3-vendor.89386f0`, with its own Zod 3 dependency. The adapter follows installed declarations for daily summary, consumed items, product/recipe references and meal images. It verifies meal-image capability before sync so an incompatible SDK cannot silently clear photo slots. The image includes the same SDK and an offline capability smoke check.

The OWNER connects at `/settings#connection` over HTTPS. `POST /api/yazio/connect` requires `{email,password,timezone,initialFrom}`, validates owner scope before and after credential exchange, saves the encrypted token, enables its schedule and performs server backfill. Submit is the explicit action; no storage checkbox or hidden confirmation field exists. The result distinguishes failed food loading from incomplete photographs while retaining a successful connection. Passwords stay in request memory and are cleared from the form; the SDK account projection is cached in process memory, without raw profile persistence. JSON import requires `{token,timezone,initialFrom}`. Disconnect alone requires `{confirmed:true}`. Public registration remains disabled. SDK expiry metadata is never guessed.

`fileTokenStore(path, ownerId, secret)` stores strict version-1 AES-256-GCM envelopes with random 12-byte nonce, 16-byte tag and authenticated owner/context/version/generation. HKDF-SHA256 derives the key from the existing `BETTER_AUTH_SECRET`; no new persistent key is generated. Writes are atomic with mode 0600 (new directory 0700), serialized per path in the supported single process. The operator configures `YAZIO_TOKEN_FILE` outside Git/public/uploads after explicit approval. The approved deployment path is `/app/data/yazio-token.json`; the operator keeps it outside the repository and public/upload directories. There is no plaintext fallback. Raw JSON is not a store format; explicit token import encrypts the validated token.

`src/server/yazio/client.ts` shares one in-flight authentication/refresh per client and awaits persistence even though the SDK does not await its `onRefresh` callback. Callback rejections are handled and upstream errors are generic. Loaded connection generations are checked before/after authentication and on saves. Confirmed `POST /api/yazio/disconnect` writes an authenticated encrypted null tombstone and rotates generation; stale refresh/delayed connect cannot resurrect tokens. Disconnect preserves nutrition snapshots/photos. Backup/restart must retain the encrypted file, the same auth secret and owner identity; secret rotation requires explicit migration or reconnect, never silent fallback.

Owner-only `/api/yazio/status` reads configured storage, validated token presence, persisted food/photo status, safe cached account metadata and schedule metadata. It performs no token refresh, upstream call or adoption. It does not by itself prove upstream connectivity; successful sync does. Browser responses expose no tokens or filesystem paths.

Manual sync and the single production Node timer call the same OWNER-checked runtime. A durable UUID/epoch/expiry lease is acquired before loading or refreshing stored credentials. Pending sibling operations drain before lease release, and expired/stale generations cannot write cache, snapshots, status or tokens. Manual ranges are inclusive, up to 366 days, and persist the latest explicit start/timezone. Every four hours, scheduled runs refresh local today and yesterday, clipped to that start, and repair missing historical parts. Persisted per-day food/photo/steps/weight/body checkpoints skip ready history; manual ranges use the same selection, while selected-day refresh forces every part. Registration performs no eager work; a delayed 30-second app poll adopts an existing configured connection only when no schedule row exists, with UTC fallback. Existing disabled rows remain disabled. No browser, external cron or extra credentials are needed. Four-hour retries distinguish `PHOTO_INCOMPLETE` from food failures, and last success denotes complete food loading. See `docs/nutrition-scheduler.md`.

Validated payloads are normalized to exact decimal contracts before persistence; display formatting never changes stored arithmetic. Fetch/reference/normalization failures preserve the old snapshot. Successful food loading can replace a day even when a photo transfer fails, retaining its previous YAZIO slot and all manual photos; `completedDates`, `skippedDates`, `failedDates` and required `photoFailedDates` distinguish those outcomes. An incomplete empty update conservatively retains an existing snapshot and reports failure. A fully successful empty response removes prior upstream entries/photos while preserving manual photos. The additive status migration adds the required media array to existing history without rewriting prior outcomes.

Image fetches require checked HTTPS `images.yazio-cdn.com` URLs, pin a validated public DNS address, reject redirects and never forward bearer tokens to the CDN. JPEG/PNG/WebP must match signatures and byte limits. Content-addressed files use mode 0600 under a private 0700 directory. Read handlers authorize owner scope and recheck grants after file I/O. Browser metadata omits source URLs/storage keys. Unreferenced files remain; physical garbage collection is an operator concern. Interrupted transport may recover within 45 seconds using at most 64 fresh HTTPS ranges of 8 KiB, with exact range/length, a stable strong ETag and If-Range. Redirects, HTTP denial and invalid validation never use recovery; no partial or mixed-version image is stored.

Public readers in `@/server/nutrition` require headers and owner ID, including `nutritionDayExists()` for comments. Trainers may read with current grants but cannot sync, manage tokens or mutate manual photos. Mutations enforce same origin. Versioned migrations create snapshots/cache/status/photo metadata; tests use genuine migrations. Root Vitest includes the nutrition-sync suite.

Tests use synthetic OAuth/upstream and real login/grant/revocation scenarios, not the owner's upstream records or credentials. The connection browser regression is included in root Vitest/CI and exercises SDK exchange, encrypted save, failure/busy reset, unconfigured explanation and confirmed disconnect. After separately approved store setup and deployment, the user supplies their own account credentials and verifies status, bounded sync, diary totals/issues and private photos through real HTTPS. API details are in [nutrition sync](../nutrition-sync.md).

The owner selects a visible start date (default seven inclusive days) and connects plus loads through local today. Sync period end is optional and resolved by the server in the validated IANA timezone supplied by the hydrated browser, with UTC fallback. Future/reversed/oversized requests fail before upstream preparation. A successful connection stays connected if loading fails; manual Update diary does not repeat storage consent. The server schedule runs independently of the browser.
