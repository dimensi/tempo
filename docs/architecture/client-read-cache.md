# Клиентский кеш чтения

Источник решений — [ADR 002](../decisions/002-resilient-client-reads.md). Модель реализована обычными страницами Next.js и общим клиентским store. Старые shell/task документы удалены, их требования не распространяются на новые задачи.

## Открытый экран и данные

Next.js App Router выбирает страницы и обслуживает историю. Чтение данных использует единый типизированный ресурс: `useReadResource(resource, initialSeed?)` возвращает `{ data, coverage, refreshing, error, refresh }`.

Определения ресурсов содержат ключ/параметры, разрешённый DTO и схему внутри слоя данных. Этот слой отвечает за память, IndexedDB, проверку записей/ответов, дедупликацию и обновление. UI не передаёт собственный parser и не реализует выбор disk/network или session/grant-проверки.

1. Опубликовать значение из памяти или IndexedDB для текущего аккаунта, не ожидая сети.
2. Обновить ресурс обычным авторизованным API. Неизменившиеся данные сохраняют ссылки; редактируемые поля не переинициализируются.
3. При сетевом сбое/5xx оставить прежние данные. Если данных нет, показать состояние ресурса с повтором.
4. При подтверждённом удалении обновить конкретный ресурс. Отсутствие записи в partial-выборке не доказывает удаление.

Сохраняются только фактически загруженные ресурсы: без запросов за весь период, отдельной медицинской сводки для прогрева и подготовки непосещённых деталей. Существующие ограничения памяти 200 ресурсов / 14 МиБ сохраняются как бюджет, а не обещание покрытия истории. На диске также нужны квоты и вытеснение; отказ записи не стирает рабочую модель. Credentials и signed provider URLs не являются кешируемыми данными.

## Состояние взаимодействия

Композиция экранов находится рядом с соответствующими `page.tsx`; связанные detail-маршруты могут использовать общий клиентский экран внутри своего раздела. Общего каталога страниц и выбора экрана по URL нет. В компоненте GET-данные читаются непосредственно из `useReadResource`, без второго загрузочного эффекта и зеркала DTO в `useState`. Мутация обновляет или перечитывает тот же ресурс; локальный state предназначен для редактирования и результатов отдельных действий.

Даты/фильтры остаются в URL и читаются штатными Next hooks. Черновики, раскрытия и необходимое UI-состояние живут отдельно от GET-кеша, с ограничением размера и разделением аккаунтов. Их можно восстановить после обычного remount страницы. Для открытой формы сохраняется и контекст редактирования, а не только поля; reconnect сам по себе её не закрывает. Сеть не управляет типом renderer или ключом формы.

Нет постоянного network label, времени кеша над каждым экраном и общего offline-alert. Недоступное действие показывает конкретную причину рядом с действием. Уже существующие очереди и конфликты остаются видимыми в своих формах.

## Авторизация и сброс

Серверный guard/middleware проверяет сессию и разрешения. Общий клиентский API-слой обрабатывает `AUTH_REQUIRED`/`ACCESS_REVOKED` единым logout, а `FORBIDDEN` оставляет ошибкой действия. Не интерпретировать все 403/409 как глобальный logout. Коды классифицирует общий серверный API-обработчик; серверные проверки остаются в guards и предметных handlers.

Reconnect, foreground и pageshow вызывают одну объединённую фоновую проверку доступа. Сетевой сбой не закрывает кеш; подтверждённый отказ очищает состояние. До получения отказа скачанные данные тренера могут оставаться доступными, в том числе после BFCache restore. Отдельного conceal/reveal протокола, локальной проверки срока grant или блокировки экранов во время identity refresh нет.

Кеш разделён по аккаунту; logout/account switch меняют локальное поколение запросов, поэтому старый ответ не восстанавливает очищенный store. Очистку выполняет клиент, а не серверный Proxy. Offline logout сохраняет sign-out intent до ответа сервера. Оповещения вкладок о сбросе достаточны без гарантии следующего кадра.

Durable queue описана отдельно в [offline writes](offline-writes.md). Сброс read cache не удаляет pending writes. Logout с удалением записей устройства следует явному выбору пользователя; очередь одного аккаунта не отправляется другим.

## Навигация, файлы и запуск

Гарантия относится к данным уже доступного экрана. Нет обязательства запустить приложение без сети или открыть маршрут, ресурсы которого Next.js не загрузил. Не добавлять Workspace Router, offline entry, публичный shell, перехват ссылок или бесконечный Activity-кеш ради этих сценариев.

Общий ограниченный дедлайн и дедупликация применяются к JSON read-ресурсам. Скачивание файлов использует сигнал вызывающего кода до завершения чтения тела ответа.

Явное сохранение PDF/video — отдельная существующая возможность, не основание возвращать shell, массовое скачивание или полное offline-покрытие. Если приложение загрузилось, существующие сохранённые файлы могут использоваться; открытие их из холодного приложения без сети не гарантируется. Установленная PWA не меняет этот контракт.

При удалении старого SW снять его регистрацию/обслуживание и удалить только принадлежащие приложению shell-кеши. Не очищать чужие кеши, durable queue и пользовательские файлы как побочный эффект обновления. По прежнему адресу `/offline-sw.js` публикуется retirement worker без fetch-перехватчика и автоматического reload.

## Приёмка

- Открыть ресурс онлайн; задержать следующее чтение: кеш виден до сетевого ответа.
- Повторить с недоступным origin при `navigator.onLine=true`; прежние данные и черновик остаются.
- Восстановить сеть: данные обновляются без reload, повторной навигации и сброса ввода.
- Проверить обычный Back/Forward, URL-даты, раскрытия и восстановление черновика после перехода.
- Войти реальным TRAINER, отозвать grant и вернуть связь: сервер запрещает новые данные, общий обработчик очищает кеш после обнаружения отказа. Старые локальные данные до отказа допустимы.
- Проверить logout, account switch, поздний ответ старого аккаунта, отказ IndexedDB и сохранность pending writes при обновлении SW.

Нет приёмки cold offline boot, полного периода, автономных detail-маршрутов, синхронного скрытия порталов или ожидания всех старых окон ради shell. Для runtime-рефакторинга применяется Full tier и пересмотренный production-набор сетевой устойчивости. Для одних Markdown-изменений применяется Docs-only.
