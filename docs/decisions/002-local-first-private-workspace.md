# ADR 002: непрерывный local-first интерфейс приватных экранов

Дата: 2026-10-16. Статус: принято.

## Контекст

Приложение уже хранит безопасную браузерную проекцию, проверяет OWNER/TRAINER scope, очищает её при logout, смене аккаунта или отзыве доступа и имеет отдельную идемпотентную очередь OWNER-записей. Однако сам факт проверки сети или сессии не должен превращать готовый экран в loader, менять React-дерево или сбрасывать пользовательский ввод.

Основные локальные экраны — дневник, тренировки, замеры и аналитика. Тот же контракт применяется к остальным явно разрешённым read-проекциям. Неизвестные данные не угадываются и не подменяются пустыми.

## Решение

### Независимые состояния

Модель чтения всегда разделяет четыре оси:

- доступ: `unknown`, `locally-allowed`, `checking`, `confirmed`, `denied`;
- покрытие данных: `missing`, `partial`, `complete`;
- обновление: `idle`, `refreshing`, `failed`;
- соединение: `unknown`, `reachable`, `unreachable`.

`refreshing` и `unreachable` не удаляют подтверждённые `data`. Полноэкранный loading допустим только когда одновременно нет локального значения и ещё не завершена необходимая проверка доступа. Статус проверки и синхронизации показывается отдельно от данных.

### Один экран и один read store

Online, offline и server seed используют общие view-компоненты и `ReadResourceStore`. RSC остаётся источником начального авторизованного seed и серверным fallback, но не является обязательным переходом для уже сохранённого URL.

При выборе сохранённого read-route клиент сначала меняет обычный URL и показывает fenced IndexedDB/memory projection. Identity и обычная Next.js-навигация продолжаются в фоне. Shared layout и текущая форма не заменяются pending-экраном только из-за нестабильной сети.

CacheStorage содержит только публичную оболочку и статические assets. Приватные DTO, RSC и API-ответы сохраняются только через явный whitelist контрактов в IndexedDB.

### Reconcile вместо сброса

Транспорт может возвращать полный snapshot. Клиент применяет его как change set:

- `complete` разрешает удалить отсутствующие записи только внутри покрытого query;
- `partial` добавляет и обновляет записи, но не доказывает удаление;
- неизменившиеся записи сохраняют идентичность;
- невалидный ответ не публикуется;
- запись в IndexedDB атомарна, а quota/eviction не уничтожает рабочую модель в памяти.

Версия, coverage и `savedAt` являются частью интерфейса read resource. `null`, ноль, пустая подтверждённая выборка и неизвестное значение различаются.

### Состояние взаимодействия

Потеря или восстановление сети не размонтирует текущий экран. Выбранная дата остаётся в URL. Scroll и раскрытия живут в session-scoped view state, ключованном каноническим URL. Разрешённые черновики и очередь записей хранятся отдельно от GET-кеша и ключуются access partition.

Сохранение черновика разрешается только явным whitelist. Пароли, токены, provider credentials и диагностические upstream payloads никогда не сохраняются. Входящий refresh не затирает редактируемое значение: при изменившейся серверной основе показывается конфликт.

### Безопасность

Device fence — локальное доказательство ранее подтверждённого scope, а не продление серверной сессии. Обычный `focus`, `pageshow`, reconnect или фоновая проверка переводит доступ в `checking`, сохраняя уже допустимый UI.

Logout, смена аккаунта, локально известная auth/provider mutation, подтверждённый `401/403` и несовпадение partition/generation сначала синхронно скрывают приватный root во всех вкладках, затем очищают физические данные. Каждый асинхронный ответ повторно сверяется с fence перед публикацией.

TRAINER использует ту же локальную модель с grant/connection generation. Устройство без сети не может узнать об удалённом revoke; после следующей успешной identity/grant-проверки отозванные данные скрываются до refresh и очищаются. Это ограничение показывается в документации и не маскируется TTL-обещанием.

## Следствия

- Feature UI не должен использовать `data = null` как начало повторного чтения.
- `navigator.onLine` — подсказка, а не access state и не причина сменить renderer.
- Синхронизация записи остаётся отдельным модулем с idempotency и ordering; read cache не отправляет mutations.
- Посещённые query сохраняются в пределах квот и retention. Непосещённый диапазон честно остаётся `missing`.
- Несовместимая browser-схема физически очищается и наполняется заново; старый renderer или compatibility shim не поддерживаются.
- Новые приватные read-экраны обязаны реализовать те же состояния и security tests до включения сохранения на диск.

## Отклонённые варианты

- **Скрывать данные перед каждой проверкой.** Безопасность не усиливается, если scope не менялся, но UI мигает и теряет контекст.
- **Кешировать приватные RSC/HTML в Service Worker.** Смешивает transport cache с authorization scope и затрудняет немедленную очистку.
- **Отдельное offline-приложение.** Дублирует UI и неизбежно расходится с online-поведением.
- **Серверный change log в первой версии.** Для текущих объёмов достаточно валидированного snapshot и локального reconcile; новая SQLite-схема не требуется.

## Проверяемые инварианты

1. Сохранённый экран начинает отображаться до завершения identity/RSC-запроса.
2. Потеря и восстановление сети не меняет identity смонтированного UI.
3. Refresh failure сохраняет last-known-good данные и локально показывает ошибку.
4. `401/403`, logout, account switch и scope mismatch скрывают приватные данные синхронно.
5. Offline-переход не выполняет provider request и не превращает неизвестное в пустое.
6. Background response старого scope никогда не публикуется.
