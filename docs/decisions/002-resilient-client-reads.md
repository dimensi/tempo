# ADR 002: быстрые клиентские чтения при нестабильной сети

Дата: 2026-10-16. Статус: реализовано. Финальная проверка конкретного коммита фиксируется в отчёте PR #123.

## Контекст

Приложение для владельца и разрешённого тренера должно быстро показывать уже загруженные данные и сохранять рабочий экран при плохой сети. Полноценное автономное приложение, доставка всех маршрутов без сети и немедленный отзыв скачанных копий не входят в цель.

Эта редакция заменяет прежнее решение ADR 002 о private workspace. Старое описание удалено; история доступна в Git. Workspace Router, offline shell, snapshot-прогрев и усиленный device lifecycle удалены из runtime PR #123. Композиция возвращена в `page.tsx`, локальные чтения обслуживает общий store.

## Решение

### Next.js и локальный кеш

Next.js App Router остаётся единственным маршрутизатором. Страницы выбираются через `page.tsx`, переходы выполняются штатными Link/router. Нет ручного сопоставления URL с экранами, отдельного offline entry или неограниченного удержания страниц в React Activity.

Композиция принадлежит самим `page.tsx`, включая клиентские страницы с hooks. Metadata остаётся в серверных layout. Промежуточные `page-client` и компоненты, лишь передающие вызов другой странице, не требуются. Общие функции загрузки и read hooks сохраняют повторяемую логику без отдельного дерева экранов.

Кешируются только фактически загруженные разрешённые ресурсы. Общий слой чтения публикует память/IndexedDB независимо от завершения сети, затем обновляет данные в фоне. Повторное чтение объединяется с уже выполняющимся запросом. Сетевая ошибка или 5xx не удаляет последнее корректное значение и не сбрасывает форму.

Cold offline boot, открытие неподготовленных маршрутов без сети и полнота данных за заранее выбранный период не гарантируются. Нет массового snapshot, прогрева непосещённых detail-страниц или обязательного кеширования HTML/RSC. Установка PWA сама по себе этих гарантий не добавляет.

### Контракты и UI

Backend возвращает типизированные предметные DTO и необходимые агрегированные read models, без зависимости от URL frontend-страниц. Продуктовые расчёты остаются на существующей стороне.

Схемы ответов и проверка IndexedDB находятся в слое данных. UI использует `useReadResource(resource, initialSeed?)` и получает `{ data, coverage, refreshing, error, refresh }`; не выбирает источник, не разбирает транспортные ответы и не проверяет session/grant. Валидация пользовательского ввода для обратной связи формы остаётся допустимой; сервер всё равно проверяет входные данные.

Missing, подтверждённая пустота, partial и complete различаются. Повреждённая или несовместимая запись кеша становится cache miss. Кеш ограничен по объёму; его потеря не отключает обычные серверные чтения. Пароли, токены и provider credentials не кешируются.

Дата/фильтр живут в URL. Черновики и раскрытия хранятся отдельно от GET-кеша в ограниченном хранилище текущего пользователя. Смена соединения не инициирует навигацию и не переинициализирует форму. Back/Forward выполняет Next.js; сохранение состояния не требует бессрочного удержания DOM.

### Доступ и принятый компромисс

Сервер проверяет сессию, permission и owner/grant при обращении к данным. Серверный middleware/общий guard возвращает явный код результата. Он не может самостоятельно очистить IndexedDB браузера: это делает общий клиентский API-обработчик.

Целевые коды: `AUTH_REQUIRED` (401) и `ACCESS_REVOKED` (403) запускают единый logout и очистку локального состояния; `FORBIDDEN` (403) означает запрет отдельного действия без logout. Обычный 403 или 409 сам по себе не доказывает отзыв всей сессии. Сетевая ошибка не является отказом авторизации.

На reconnect, возврате вкладки в foreground и pageshow выполняется дедуплицированная фоновая проверка. Пока сервер не подтвердил отказ, старые данные могут оставаться видимыми. Отключённый тренер может читать скачанную копию после удалённого отзыва grant; это принятый продуктовый компромисс. Гарантии скрытия до следующего кадра, проверки часов/TTL ради запрета локального чтения и специального BFCache conceal/reveal отсутствуют.

При явном logout, смене аккаунта или обнаруженном отзыве общий клиентский слой сбрасывает авторизацию, кеш и черновики. Между вкладками достаточно уведомления о сбросе, без синхронного conceal-протокола. Ключ аккаунта и локальное поколение запросов предотвращают смешение пользователей и повторное наполнение store поздним ответом завершённой сессии. Постоянные device/grant fences для каждого локального чтения не требуются.

Offline logout очищает локальное состояние и оставляет durable sign-out intent до подтверждения серверного выхода. Старую cookie-сессию нельзя автоматически восстановить поверх этого intent.

### Записи и границы

Существующая durable queue замеров и результатов тренировок сохраняется отдельно от read cache. Идемпотентность, атомарность, конфликты и проверки аккаунта перед отправкой обязательны; проверки не зависят от готовности shell или полного snapshot. Сброс только read cache не удаляет несинхронизированные записи. Явный выход с удалением данных устройства сохраняет существующее предупреждение о pending writes.

Нет смены backend, SQL-схем, продуктовых расчётов или расширения offline-записей. Удаление старого Service Worker очищает только его app-кеши и не теряет durable queue.

## Проверка решения

Проверять быстрый показ кеша при зависшем запросе, missing/empty/partial, отсутствие сброса формы, штатную навигацию, квоты, поздние ответы после logout и восстановление очереди. Реальные OWNER/TRAINER sessions проверяют серверный запрет после revoke и очистку после обнаружения отказа. Наличие старого локального содержимого до такого обнаружения допустимо.

Тесты cold offline boot, маршрутов без сети, мгновенного conceal, отката часов и SW shell readiness не являются требованиями новой модели. Они удалены или заменены сетевыми сценариями; серверные authorization и queue assertions сохранены. Проверки изменений выбираются по tiers из AGENTS.md; документация не доказывает прохождение runtime-проверок.
